# 첫 파일럿 결정 로그

[개발 로드맵](./roadmap.md)의 출시 기준을 보완할 때 검토한 선택과 이유를 기록한다. 기준 코드는 Lab `fe9336d`다. 결정은 개발 계획에 반영했고, 구체적인 운영 범위와 기준값의 승인은 출시 승인표에 남긴다.

## D01 최초 접수의 저장과 재확인

- 기존 접수는 제목과 본문으로 Ticket, Message와 AI Job을 매번 저장한다. 브라우저의 중복 클릭 방지, 내용으로 중복을 추정하는 방식, 제출 UUID를 DB에 기록하는 방식을 비교했다.
- 인증 고객의 영속 ID와 접수 UUID를 Ticket 생성 전에 식별해 PostgreSQL의 `UNIQUE` 제약으로 중복을 막는다. 제출 기록과 업무 행을 같은 트랜잭션에 넣으면 겹친 요청과 응답 유실에서도 한 번의 저장을 확인할 수 있다. [AWS 재시도 설계 지침](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)
- 화면 메모리가 원래 제출을 유지하는 동안 명시적으로 재확인한다. 화면 상태가 사라지면 내 문의와 운영자 확인으로 이어진다. 문의 원문을 브라우저에 지속 저장하는 방식은 그 보관과 접근을 별도로 설계할 때 검토한다.
- 구현 영향은 최초 접수 API·Service·저장소·Migration과 [접수 화면](../src/main/resources/static/ticket-ui.mjs)이다. 제출의 비교 기준과 기존 호출자의 전환을 정하고 G1에서 확인한다. 실데이터의 접수 키 보관·삭제는 G0의 운영 정책에 포함한다.

### D01-1 2026-11-15 최초 접수 키 저장

- 별도 접수 키 테이블과 Ticket 행에 키를 저장하는 방식을 비교했다. V14는 인증 고객의 영속 ID와 UUID를 Ticket 행에 함께 기록한다. Ticket이 있어야 접수가 성립하며, 이미 저장하는 제목과 최초 Message를 비교에 사용할 수 있어 내용 사본이나 접수 중간 상태를 따로 관리할 필요가 줄어든다.
- 이전 Migration과 기존 문의는 보존한다. 이미 등록된 문의에는 접수 UUID를 추정해 채우지 않는다. 새 고객 접수의 UUID를 검증하고, 같은 UUID의 충돌은 제목·본문의 원문으로 구분한다. 접수 키는 인증된 고객 ID와 UUID를 함께 사용해 조회한다.
- 기존 `POST /api/tickets`의 경로와 성공 응답 형식을 유지한다. PostgreSQL의 화면과 현재 요청을 보내는 검증 코드를 전환해 UUID를 필수로 받는다. 접수 응답의 문의 번호와 `Location`은 재확인에서도 유지한다. 별도 `in-memory` 제목 전용 실습의 입력은 기존 형식이다.
- 변경 대상은 접수 DTO와 Controller, [접수 Service](../src/main/java/lab/helpdesk/ticket/application/TicketReceiptApplicationService.java)와 JDBC 저장소, 다음 Flyway Migration, [접수 화면](../src/main/resources/static/ticket-ui.mjs)과 검증 코드다. 구현 시 V13 업그레이드와 동시 제출을 검증한다. 실데이터에 적용할 보관 기간, 삭제 후 재전송 처리와 계정 회수 후 접근은 G0/G2/G3에서 확인한다.

### D01-2 2026-11-15 접수 재확인과 로그인 세션

- 응답을 잃은 입력을 페이지 메모리에 둔다. 사용자가 재확인을 선택할 때 서버의 세션별 표식으로 같은 로그인 세션인지 확인한다. 여러 탭이 로그인 상태를 공유할 수 있어 새 세션에 이전 문의가 전송되지 않도록 한다.
- 세션 표식은 서버에서 무작위로 발급한다. 브라우저는 같은 세션에서 최초 제출에 사용한 CSRF 토큰을 다시 쓰므로 표식 조회 직후에 세션이 바뀌어도 서버의 CSRF 검사가 적용된다. 세션이 달라지거나 페이지를 다시 열면 '내 문의'에서 확인하는 흐름을 사용한다.
- 적용 파일은 [CSRF API](../src/main/java/lab/helpdesk/security/CsrfController.java)와 [접수 화면](../src/main/resources/static/ticket-ui.mjs)이다. 브라우저 검증에서 응답 유실 후 같은 제출의 `200`, 다른 고객 세션에서 추가 POST 0건과 소유자 목록을 확인한다. 새 인증 방식을 도입할 때는 세션 회전과 재확인 동작을 함께 검증한다.

## D02 운영자 초대와 권한 회수

- 배포 환경은 현재 설정 기반 계정을 사용한다. 기존 조직 인증을 연동하는 방법과 앱에서 개인별 계정을 관리하는 방법을 비교한다. 로그인 자격과 서비스별 직원 권한은 수명과 회수 범위가 다르다.
- 파일럿은 운영자가 개인별 초대, 복구와 비활성화를 담당하는 방식으로 진행한다. 작은 참여 범위에서 계정 발급·회수 주체와 감사 근거를 확인하기 쉽다. 인증 연동 여부와 계정 관리 권한은 2단계 구현 전에 확정한다.
- 구현 영향은 [배포 인증 구성](../src/main/java/lab/helpdesk/security/DeploymentSecurityConfiguration.java), 영속 사용자 ID 연결, 세션 처리와 서비스 권한 운영 절차다.
- 기존 세션을 사용한 회수 검증에서는 서비스 직원 권한만 잃은 고객의 본인 조회와 계정 전체 비활성화를 각각 시험한다. 재시작 뒤에도 같은 권한 판정이 유지되는지 G2에서 확인한다. [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## D03 첫 운영 DB와 학습 데이터

- 학습용 V8 스냅샷을 출발점으로 복원하는 안과 빈 전용 DB에 전체 Migration을 적용하는 안을 비교했다. V9와 V10은 기존 문의의 고객 소유권과 지원 서비스를 추정해 채우지 않는다.
- 한 조직의 지원 서비스 하나를 다루는 첫 파일럿은 새 전용 DB에서 시작한다. 운영 참여 계정과 문의의 출처를 설치 시점부터 추적할 수 있다. 기존 스냅샷을 이관하려면 격리 환경에서 신뢰할 수 있는 소유권과 서비스 매핑을 별도로 검증한다.
- 영향은 [배정·이관 계약](./ticket-assignment.md), [배포 안내](../deploy/ecs/README.md)와 새 DB 설치 및 복구 절차다. G4에서 빈 DB에 대한 Migration과 신규 접수·조회 성공을 확인하고, 이관이 승인된 경우에만 해당 이관 검증을 추가한다.

## D04 삭제와 복원 뒤 접근 제어

- 원문 삭제, 비식별화와 승인된 최소 감사 기록 보존을 데이터 종류별 선택지로 검토한다. 메시지를 참조하는 배정별 확인과 상태 변경 이력이 있고, 과거 백업에는 삭제 전 내용이 포함될 수 있다.
- 승인한 처리 방식은 참조 무결성 및 보존 범위와 함께 검증한다. 삭제 전 백업은 격리 DB에 복원하고 최신 삭제 이력을 재적용하거나 검증 가능한 동등한 절차를 수행한다. 재노출 검사를 통과한 뒤 운영 트래픽을 연결한다. 이 조건으로 복원 중의 재노출을 막는다.
- 영향은 [확인 이력 Migration](../src/main/resources/db/migration/V12__add_customer_message_confirmations.sql), [상태 이력 Migration](../src/main/resources/db/migration/V13__add_ticket_status_events.sql)과 데이터 운영·복구 절차다.
- 보관 기간, 삭제 방식과 삭제 이력의 접근·보관은 데이터 책임자가 실제 문의 전에 확정한다. G3에서는 합성 데이터의 처리와 삭제 전 백업에서의 복원 결과를 고객·직원 범위별로 대조한다.

## D05 AI 비활성과 대기 작업

- Worker와 Provider는 별도 조건으로 활성화되며 최초 접수는 AI Job 행을 저장한다. 첫 파일럿에 외부 AI를 연결하는 안과 사람이 지원 흐름을 끝까지 운영하는 안을 비교했다.
- 두 기능을 비활성으로 두고 외부 AI 자격 증명도 주입하지 않는 후보로 검증한다. 이 범위에서 고객의 문의 전송과 AI 품질 평가를 분리할 수 있다. 대기 Job은 관찰하고 실제 처리는 이후 명시적인 데이터 범위 승인과 연결한다.
- 영향은 [Worker 설정](../src/main/java/lab/helpdesk/ai/processing/AiSuggestionWorkerConfiguration.java), [Provider 설정](../src/main/java/lab/helpdesk/ai/provider/AiSuggestionProviderConfiguration.java)과 배포 후보 검증이다.
- G5에서 검증 환경의 외부 연결 관찰 결과와 Job 상태·시도 건수를 사용해 호출 및 처리 시작 0건을 확인한다. 대기 작업 건수와 비활성 설정 근거도 기록한다. 이후 활성화 검토에는 기존 Job의 처리 대상과 범위를 기록한다.

## D06 출시 승인과 중지·재개

- 로컬·CI 성공만 참조하는 안과 실행할 후보의 근거를 기준으로 승인하는 안을 비교했다. 기존 검증은 업무 구현의 근거이며 배포 환경에서의 부하와 복구 결과는 해당 후보에서 확인해야 한다.
- G0~G5를 적용하고 Commit, Image Digest, 설정과 관찰 결과를 확인한 다음 승인한다. 잠정 부하와 복구 목표를 소규모 합성 검증의 시작값으로 사용한다. 실제 운영 한도와 복구 목표는 파일럿 시작 전 G0에 확정한다.
- 권한 사고나 접수 누락·중복, 승인 범위를 넘는 AI 호출, 합의한 가용성 중지 기준이 발생하면 신규 접수를 중지한다. 권한 우회나 데이터 노출이 있으면 문제 경로도 차단한다. 수정 후보의 재검증과 책임자 승인을 거쳐 재개하면 운영자가 처리 책임과 판단 근거를 추적할 수 있다.
- 영향은 [로컬 검증 안내](./local-verification.md), [CI Workflow](../.github/workflows/verify.yml), [로드맵의 출시 기준](./roadmap.md#파일럿-출시-기준)과 운영 기록이다. 검증 시각, 관찰 값, 결과 위치와 승인자는 실제 실행 뒤에 남긴다.
