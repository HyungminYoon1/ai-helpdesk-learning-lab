# 첫 파일럿 결정 로그

[개발 로드맵](./roadmap.md)의 출시 기준을 보완할 때 검토한 선택과 이유를 기록한다. 기준 코드는 Lab `fe9336d`다. 결정은 개발 계획에 반영했고, 구체적인 운영 범위와 기준값의 승인은 출시 승인표에 남긴다.

## D01 최초 접수의 저장과 재확인

- 기존 접수는 제목과 본문으로 Ticket, Message와 AI Job을 매번 저장한다. 브라우저의 중복 클릭 방지, 내용으로 중복을 추정하는 방식, 제출 UUID를 DB에 기록하는 방식을 비교했다.
- 인증 고객의 영속 ID와 접수 UUID를 Ticket 생성 전에 식별해 PostgreSQL의 `UNIQUE` 제약으로 중복을 막는다. 제출 기록과 업무 행을 같은 트랜잭션에 넣으면 겹친 요청과 응답 유실에서도 한 번의 저장을 확인할 수 있다. [AWS 재시도 설계 지침](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)
- 화면 메모리가 원래 제출을 유지하는 동안 명시적으로 재확인한다. 화면 상태가 사라지면 내 문의와 운영자 확인으로 이어진다. 문의 원문을 브라우저에 지속 저장하는 방식은 그 보관과 접근을 별도로 설계할 때 검토한다.
- 구현 영향은 최초 접수 API·Service·저장소·Migration과 [접수 화면](../src/main/resources/static/ticket-ui.mjs)이다. 제출의 비교 기준과 기존 호출자의 전환을 정하고 G1에서 확인한다. 실데이터의 접수 키 보관·삭제는 G0의 운영 정책에 포함한다.

### D01-1 2026-11-15 최초 접수 키 저장

- 별도 접수 키 테이블과 Ticket 행에 키를 저장하는 방식을 비교했다. V14는 인증 고객의 영속 ID와 UUID를 Ticket 행에 함께 기록한다. Ticket이 있어야 접수가 성립하며, 이미 저장하는 제목과 최초 Message를 비교에 사용할 수 있어 내용 사본이나 접수 중간 상태를 따로 관리할 필요가 줄어든다.
- 이전 Migration과 기존 문의는 보존한다. 이미 등록된 문의에는 접수 UUID를 추정해 채우지 않는다. 새 고객 접수의 UUID를 검증하고, 같은 UUID의 충돌은 제목·본문의 원문으로 구분한다. 접수 키는 인증된 고객 ID와 UUID를 함께 사용해 조회한다.
- 기존 `POST /api/tickets`의 경로와 성공 응답 형식을 유지한다. PostgreSQL의 화면과 현재 요청을 보내는 검증 코드를 전환해 UUID를 필수로 받는다. 접수 응답의 문의 번호와 `Location`은 재확인에서도 유지한다. 별도 `in-memory` 제목 전용 실습의 입력은 기존 형식이다.
- 변경 대상은 접수 DTO와 Controller, [접수 Service](../src/main/java/lab/helpdesk/ticket/application/TicketReceiptApplicationService.java)와 JDBC 저장소, 다음 Flyway Migration, [접수 화면](../src/main/resources/static/ticket-ui.mjs)과 검증 코드다. 구현 시 V13 업그레이드와 동시 제출을 검증한다. 실데이터에 적용할 보관 기간, 삭제 후 재전송 처리와 계정 회수 후 접근은 G0/G2/G3에서 확인한다.

### D01-2 2026-11-15 접수 재확인과 로그인 세션

- 응답을 잃은 입력을 페이지 메모리에 둔다. 사용자가 재확인을 선택할 때 서버의 세션별 표식으로 같은 로그인 세션인지 확인한다. 여러 탭이 로그인 상태를 공유할 수 있어 새 세션에 이전 문의가 전송되지 않도록 한다.
- 세션 표식은 서버에서 무작위로 발급한다. 브라우저는 같은 세션에서 최초 제출에 사용한 CSRF 토큰을 다시 쓰므로 표식 조회 직후에 세션이 바뀌어도 서버의 CSRF 검사가 적용된다. 세션이 달라지거나 페이지를 다시 열면 '내 문의'에서 확인하는 흐름을 사용한다.
- 적용 파일은 [CSRF API](../src/main/java/lab/helpdesk/security/CsrfController.java)와 [접수 화면](../src/main/resources/static/ticket-ui.mjs)이다. 브라우저 검증에서 응답 유실 후 같은 제출의 `200`, 다른 고객 세션에서 추가 POST 0건과 소유자 목록을 확인한다. 새 인증 방식을 도입할 때는 세션 회전과 재확인 동작을 함께 검증한다.

## D02 운영자 초대와 권한 회수

### D02-1 2026-11-15 개인별 로그인과 첫 계정 관리자

- 현재 배포는 설정 기반 학습 계정을 생성한다. 이 방식을 파일럿에 이어 쓰는 안, Helpdesk가 비밀번호와 인증 요소를 보관하는 안, 관리형 OIDC에 인증을 맡기는 안을 비교했다.
- OIDC를 사용하고 Helpdesk는 서버 세션과 CSRF 보호를 유지한다. Helpdesk DB의 영속 사용자 ID를 `iss`·`sub`와 연결해 이메일 변경으로 소유권이 바뀌지 않게 한다. 서비스별 권한은 DB에서 관리하며, 직원과 계정 관리자는 제공자에서 MFA를 강제한다.
- 첫 계정 관리자는 프로젝트 운영자 본인으로 확정했다. 승인한 본인 신원을 초기 설정에서 연결하며, 서비스 지원관리자나 클라우드 운영 권한은 각자 필요한 책임을 기준으로 부여한다.
- 영향은 [배포 인증 구성](../src/main/java/lab/helpdesk/security/DeploymentSecurityConfiguration.java), 사용자 신원 연결, 세션과 서비스 권한 경계다. G2에서 개인별 권한과 첫 관리자 권한을 검증한다. [개인 계정 설계](./pilot-account-design.md#인증과-서비스-권한)

### D02-2 2026-11-15 초대·복구·비활성화

- 공개 가입과 운영자 초대, 앱 내부 비밀번호 복구와 제공자 복구, 역할 회수와 계정 전체 비활성화를 각각 검토했다. 제한된 참여 범위에서 역할 부여와 회수의 책임을 추적할 수 있게 운영자 초대로 시작한다.
- 일회용 앱 초대는 해시로 저장하고 24시간 동안 유효하게 한다. 시간·주소·이메일 검증을 통과한 수락과 신원·권한 연결을 함께 커밋한다. 재발급은 이전 미사용 초대를 폐기한다. 비밀번호와 MFA 복구는 제공자 절차를 이용하고, 앱 접근 복구와 신원 재연결은 검증 후 감사 기록에 남긴다.
- 계정 전체 비활성화는 DB의 계정 상태와 세션 버전을 사용해 기존 세션과 이후 로그인을 차단한다. 서비스 직원 권한만 회수하면 해당 서비스의 직원 권한이 사라지며, 로그인 자격이 유효한 사람의 본인 문의는 계속 읽을 수 있다. 이미 저장된 문의와 이력은 내부 사용자 ID에 남는다.
- 영향은 초대·회수 이력, 계정·세션 판정, 고객의 소유권 검사와 운영 안내다. G2에서 초대 재사용, 권한 회수가 커밋된 이후의 보호 요청, 재시작 뒤의 회수 상태까지 확인한다. [초대와 회수 계약](./pilot-account-design.md#초대와-회수)

### D02-3 2026-11-15 첫 파일럿 OIDC 제공자

- 외부 이메일 초대, 직원 MFA와 13~14명 기준 비용으로 Cognito Lite, Auth0 Essentials, Entra Workforce B2B를 비교했다. 관리형 서비스 비용과 고객이 겪는 초기 TOTP 등록을 함께 검토했다.
- 서울 Cognito Lite 단일 User Pool을 첫 파일럿 제공자로 확정했다. Gmail 별칭으로 받은 관리자 초대, 두 계정의 이메일 검증, 필수 TOTP와 기기 분실 뒤 동일 신원으로 복귀를 실제로 확인했다. 조건에 맞는 무료 사용량이 있을 때 인증 기본료는 월 $0으로 예상한다.
- 첫 토큰 발급 때 고객의 이메일과 TOTP가 아직 확인되지 않은 동작을 관찰했다. 그 토큰을 온보딩에만 사용하고 이메일 코드 검증과 기존 로그인 세션 종료 후 새 OIDC 로그인에서 TOTP를 완료해야 초대를 수락하도록 한다. 이 흐름의 App 권한 경계와 중복 수락 방지는 G2에서 확인한다.
- 기존 사람용 역할이 없어 프로젝트 운영자가 승인한 검증 전용 IAM 역할만 준비했다. MFA와 시간·리전을 제한하고 Pool 생성 뒤 권한을 해당 Pool ARN으로 좁혔다. 역할과 Pool은 향후 운영 인증 경계와 분리한다. 영향은 [개인 계정 설계와 검증 기록](./pilot-account-design.md#서울-cognito-검증-기록), 초대 처리, 운영자의 MFA 분실 복구 안내다.

### D02-4 2026-11-15 첫 세션을 제한하는 Cognito 연동

- Cognito 토큰을 곧바로 앱 세션으로 쓰는 안과, 온보딩 상태를 분리해 이메일 확인 및 두 번째 로그인을 검증하는 안을 비교했다. Spring Security에 Code·PKCE·nonce 처리를 맡기고 재로그인과 초대 수락이 완료될 때 Helpdesk 세션을 발급한다.
- Hosted UI 로그아웃을 거쳐 새 `state`를 생성하고 `auth_time`, 동일 `iss`·`sub`, 검증된 이메일을 확인한다. Cognito에는 지원하는 MFA를 설정하며 App은 지정 Pool의 필수 TOTP와 Cognito 전용 Client 설정을 재조회해 이 전제를 확인한다.
- V15에서 초대 해시·발급/수락 시각·운영자와 수신 계정을 저장한다. 한 주소의 미사용 초대는 재발급 시 회수하고, 초대 사용·신원 연결·서비스 역할 부여는 한 트랜잭션으로 저장한다. 최초 계정 관리자도 온보딩을 통과하며 DB에서 단일 초기 관리자만 허용한다.
- 권한 회수를 검토하면서 API만 활성 멤버십을 다시 읽는 방식과 화면에도 같은 기준을 적용하는 방식을 비교했다. 기존 세션으로 권한 회수 전의 직원 화면이 열리지 않도록 [보안 설정](../src/main/java/lab/helpdesk/security/SecurityConfiguration.java)의 보호 경로 기준을 [계정 검사](../src/main/java/lab/helpdesk/cognito/CognitoLogin.java)에도 적용한다. 로컬에서 같은 세션의 직원 화면과 API 차단, 고객 기능 유지 여부를 검사하고 G2에서 브라우저로 재확인한다.
- 검증용 서울 Pool의 합성 계정 두 개, 앱 클라이언트와 도메인, Pool, 임시 IAM 역할을 삭제하고 AWS 조회로 확인했다. 연동은 [로컬 OIDC·PostgreSQL 검증](./pilot-account-design.md#helpdesk-연동)에서 확인했다. 운영 App 연결과 복구·비활성화 운영 절차는 G2 출시 후보에서 확인한다.

### D02-5 2026-11-15 계정 상태와 세션 재발급

- 보호 요청에서 계정 상태만 읽는 안과 세션 발급 버전도 대조하는 안을 비교했다. 상태와 버전을 함께 확인해, 비활성화 중에 요청을 보내지 않은 세션도 재활성화 뒤 다시 사용되지 않게 한다. 서비스 권한과 같은 DB 조회에서 판정한다.
- Cognito 콜백이 돌아올 때 현재 계정 상태를 확인하고, 재활성화 시각 뒤에 서명된 `auth_time`만 새 인증으로 인정한다. 이전 Cognito 로그인으로 돌아오면 지정된 Hosted UI의 로그아웃 경로를 거쳐 다시 로그인하게 한다.
- [V16 마이그레이션](../src/main/resources/db/migration/V16__add_cognito_account_state_and_session_version.sql), [세션 검사](../src/main/java/lab/helpdesk/cognito/CognitoLogin.java), [로그인 처리](../src/main/java/lab/helpdesk/cognito/CognitoOnboarding.java)에 적용했다. 로컬 OIDC와 PostgreSQL로 로그인 경계를 검사하고, G2에서 실제 Cognito 로그인과 여러 브라우저 세션으로 재확인한다.

### D02-6 2026-11-15 관리자 계정 상태 변경과 감사 이력

- 관리자 명령을 마지막 요청의 값으로 덮어쓰는 방식과, 조회한 버전을 확인한 뒤 변경하는 방식을 비교했다. 목록에서 확인한 계정 키와 세션 버전으로 요청하고 대상 계정의 행 잠금 아래에서 버전을 검사한다. 같은 상태의 재요청은 버전이 같으면 조회 결과를 반환하고, 이전 버전이면 현재 DB 상태를 다시 확인하도록 충돌을 반환한다.
- 계정 변경과 감사 이력을 한 트랜잭션으로 저장한다. 사유는 고정 코드로 남기고, 계정 키와 초대 당시 주소는 활성 계정 관리자에게만 제공한다. 파일럿의 첫 관리자는 단일 계정이므로 이 API에서 비활성화를 거부한다. 문의 소유권과 작성 이력의 참조는 내부 계정 ID로 보존한다.
- [관리자 API와 사용 계약](./pilot-account-design.md#계정-관리자-api), [계정 서비스](../src/main/java/lab/helpdesk/cognito/CognitoAccounts.java), [V17 감사 이력](../src/main/resources/db/migration/V17__record_cognito_account_status_changes.sql)에 적용했다. 로컬에서 관리자 권한, CSRF, 버전 충돌, 커밋 실패와 이전 세션 차단을 확인한다. 실제 Cognito 로그인과 첫 관리자 복구는 G2에서 점검한다.

### D02-7 2026-11-16 관리자 승인형 Cognito 복구 계획

- 이메일 코드로 사용자가 시작하는 복구와 관리자가 본인 확인 뒤 시작하는 복구를 검토했다. 파일럿은 Helpdesk에서 계정을 잠그고 기존 세션을 먼저 차단할 수 있도록 `admin_only`와 관리자 승인형 임시 비밀번호를 권장한다. Cognito가 자격 증명 변경과 MFA 검증을 맡고, Helpdesk는 복구 진행과 접근 재개 승인을 기록한다. [Cognito 복구 설정](https://docs.aws.amazon.com/cognito/latest/developerguide/managing-users-passwords.html)
- 첫 계정 관리자가 인증기를 잃으면 일반 관리자 작업에 필요한 Helpdesk 세션을 만들 수 없다. 지정 Pool과 기존 첫 관리자 신원으로 범위를 좁힌 독립 AWS 운영자 경로를 출시 전에 준비하는 안을 선택했다.
- 영향 범위는 계정 상태와 감사 이력, Cognito 연동, 재인증과 첫 관리자 운영 절차다. 로컬에서는 복구 시작 커밋 실패, AWS 응답 유실, 이전 세션 차단을 검증한다. G2에서는 격리 Cognito Lite를 Helpdesk에 연결해 첫 관리자 세션이 없는 상태부터 복구를 끝까지 수행한다. [후속 구현 계획](./pilot-account-design.md#cognito-계정-복구-구현-계획)

### D02-8 2026-11-18 V18 복구 요청과 세션 차단

- 재시도마다 새 이력을 만드는 방식과 기존 제출을 다시 읽는 방식을 검토했다. 관리자와 대상, 제출 UUID로 기존 결과를 찾고 원래 요청 내용이 일치할 때 같은 접수를 반환한다. 대상 계정 행을 잠그고 진행 중인 복구가 한 건이도록 DB에서도 제약한다.
- 처음 시작할 때는 이전 상태와 감사 이력, 계정 잠금과 세션 버전 증가를 한 트랜잭션으로 저장한다. 비활성 계정을 복구 전에 다시 열 필요가 없도록 `DISABLED`에서도 시작하고 이전 상태를 기록한다. 복구 대기의 해제와 첫 관리자의 복구는 별도의 승인 경로를 따른다.
- [V18 마이그레이션](../src/main/resources/db/migration/V18__start_cognito_account_recovery.sql)과 [복구 시작 서비스](../src/main/java/lab/helpdesk/cognito/CognitoAccounts.java)에 적용했다. 로컬 통합 테스트로 저장 경계와 중복 접수를 확인했다. 후속 검토는 Cognito 호출과 결과 재확인, 새 인증과 접근 재개 승인이다. [V18 API](./pilot-account-design.md#v18-복구-요청-api)

## D03 첫 운영 DB와 학습 데이터

- 학습용 V8 스냅샷을 출발점으로 복원하는 안과 빈 전용 DB에 전체 Migration을 적용하는 안을 비교했다. V9와 V10은 기존 문의의 고객 소유권과 지원 서비스를 추정해 채우지 않는다.
- 한 조직의 지원 서비스 하나를 다루는 첫 파일럿은 새 전용 DB에서 시작한다. 운영 참여 계정과 문의의 출처를 설치 시점부터 추적할 수 있다. 기존 스냅샷을 이관하려면 격리 환경에서 신뢰할 수 있는 소유권과 서비스 매핑을 별도로 검증한다.
- 영향은 [배정·이관 계약](./ticket-assignment.md), [배포 안내](../deploy/ecs/README.md)와 새 DB 설치 및 복구 절차다. G4에서 빈 DB에 대한 Migration과 신규 접수·조회 성공을 확인하고, 이관이 승인된 경우에만 해당 이관 검증을 추가한다.

## D04 삭제와 복원 뒤 접근 제어

- 원문 삭제, 비식별화와 승인된 최소 감사 기록 보존을 데이터 종류별 선택지로 검토한다. 메시지를 참조하는 배정별 확인과 상태 변경 이력이 있고, 과거 백업에는 삭제 전 내용이 포함될 수 있다.
- 승인한 처리 방식은 참조 무결성 및 보존 범위와 함께 검증한다. 삭제 전 백업은 격리 DB에 복원하고 최신 삭제 이력을 재적용하거나 검증 가능한 동등한 절차를 수행한다. 재노출 검사를 통과한 뒤 운영 트래픽을 연결한다. 이 조건으로 복원 중의 재노출을 막는다.
- 영향은 [확인 이력 Migration](../src/main/resources/db/migration/V12__add_customer_message_confirmations.sql), [상태 이력 Migration](../src/main/resources/db/migration/V13__add_ticket_status_events.sql)과 데이터 운영·복구 절차다.
- 보관 기간, 삭제 방식과 삭제 이력의 접근·보관은 데이터 책임자가 실제 문의 전에 확정한다. G3에서는 합성 데이터의 처리와 삭제 전 백업에서의 복원 결과를 고객·직원 범위별로 대조한다.

## D05 AI 비활성과 대기 작업

- Worker와 Provider는 별도 조건으로 활성화되며 최초 접수는 AI Job 행을 저장한다. 첫 파일럿에 외부 AI를 연결하는 안과 사람이 지원 흐름을 끝까지 운영하는 안을 비교했다.
- 두 기능을 비활성으로 두고 외부 AI 자격 증명도 주입하지 않는 후보로 검증한다. 이 범위에서 고객의 문의 전송과 AI 품질 평가를 분리할 수 있다. 대기 Job은 관찰하고 실제 처리는 이후 명시적인 데이터 범위 승인과 연결한다.
- 영향은 [Worker 설정](../src/main/java/lab/helpdesk/ai/processing/AiSuggestionWorkerConfiguration.java), [Provider 설정](../src/main/java/lab/helpdesk/ai/provider/AiSuggestionProviderConfiguration.java)과 배포 후보 검증이다.
- G5에서 검증 환경의 외부 연결 관찰 결과와 Job 상태·시도 건수를 사용해 호출 및 처리 시작 0건을 확인한다. 대기 작업 건수와 비활성 설정 근거도 기록한다. 이후 활성화 검토에는 기존 Job의 처리 대상과 범위를 기록한다.

## D06 출시 승인과 중지·재개

- 로컬·CI 성공만 참조하는 안과 실행할 후보의 근거를 기준으로 승인하는 안을 비교했다. 기존 검증은 업무 구현의 근거이며 배포 환경에서의 부하와 복구 결과는 해당 후보에서 확인해야 한다.
- G0~G5를 적용하고 Commit, Image Digest, 설정과 관찰 결과를 확인한 다음 승인한다. 잠정 부하와 복구 목표를 소규모 합성 검증의 시작값으로 사용한다. 실제 운영 한도와 복구 목표는 파일럿 시작 전 G0에 확정한다.
- 권한 사고나 접수 누락·중복, 승인 범위를 넘는 AI 호출, 합의한 가용성 중지 기준이 발생하면 신규 접수를 중지한다. 권한 우회나 데이터 노출이 있으면 문제 경로도 차단한다. 수정 후보의 재검증과 책임자 승인을 거쳐 재개하면 운영자가 처리 책임과 판단 근거를 추적할 수 있다.
- 영향은 [로컬 검증 안내](./local-verification.md), [CI Workflow](../.github/workflows/verify.yml), [로드맵의 출시 기준](./roadmap.md#파일럿-출시-기준)과 운영 기록이다. 검증 시각, 관찰 값, 결과 위치와 승인자는 실제 실행 뒤에 남긴다.
