## 첫 파일럿 범위

- 한 운영 조직의 지원 서비스 하나에서 초대받은 고객, 담당 직원, 해당 서비스의 지원관리자가 참여한다. 브라우저로 텍스트 문의를 접수하고 본인 문의와 답변을 확인한다. 대상 서비스는 운영 설정으로 지정한다.
- 현재 담당자가 공식 답변을 작성한다. 해결할 때는 최신 고객 글까지 명시적으로 확인한 범위와 관련 공식 답변, 해결 사유를 남긴다. 미해결인 경우 기존 권한 계약에 따라 명시적으로 재개한다. [상태 변경 계약](./ticket-status.md)
- 첫 운영은 새 전용 DB에서 시작한다. 합성 데이터가 들어 있는 학습용 스냅샷은 이관 검증이 필요한 경우 격리 환경에서 사용한다. 민감 내부 문의는 별도 접근 권한이 확정된 범위에서 다룬다.
- AI Worker와 외부 Provider는 비활성 상태로 시작한다. 접수로 쌓이는 AI 작업 행은 대기 상태와 건수를 확인한다. 실제 문의를 AI에 보내는 범위는 별도 승인 대상으로 관리한다.

## 착수 일정

2026-11-15에 확인한 개발 기준은 Lab `ae2a307`과 V13까지의 Flyway Migration이다. 문의 접수부터 공식 답변, 인계, 후속 글, 확인과 해결·재개는 이미 구현되어 있다. 첫 과업은 최초 접수의 응답을 잃었을 때 이미 저장된 문의를 다시 찾는 기능이다.

기존 회고의 주 6시간을 기준으로, 착수 후 8주까지 검토와 검증을 배치했다. 운영 조건은 기능 개발과 병행해 결정하고, 실제 운영 시작일은 출시 승인 뒤 정한다.

| 작업 창 | 작업과 산출물 | 다음 단계로 넘어갈 기준 |
|---|---|---|
| 1–2주 | 최초 접수 재확인. PostgreSQL 저장, HTTP 계약, 고객 화면과 회귀 검증 | 동시 제출과 응답 유실에서도 같은 문의 번호를 받는다. 저장 건수와 Rollback을 DB에서 확인한다. |
| 3–4주 | 개인별 계정 운영과 고객·직원 화면 연결. 인증 방식 결정, 초대·복구·비활성화, 미배정 문의 처리 | 두 고객과 두 직원, 관리자 계정으로 조회 경계와 권한 회수 뒤 동작을 확인한다. 고객이 번호를 외우지 않고 문의를 찾고, 담당자가 접수부터 재개까지 처리한다. |
| 5–6주 | 개인정보 보호와 운영 절차. 보관·삭제 정책, 요청 제한, 오류와 로그, 장애 대응 안내 | 합성 데이터를 삭제하고 삭제 전 백업을 격리 복원해 재노출이 없고 남겨야 할 참조가 유효한지 확인한다. |
| 7–8주 | 승인된 검증 환경에 파일럿 후보 배포. 신규 DB 설치, HTTPS, 부하, 백업 복구, 앱 복귀 | 후보 Commit·CI·실행 Digest를 대조한다. 합의한 부하와 복구 목표, AI 호출 및 Job 처리 시작 0건, 중지·재개 훈련의 근거를 G0~G5로 검토한다. |

실제 파일럿의 대상 서비스와 책임자, 데이터 보관, 운영 예산은 G0에서 확정한다. 로컬 합성 데이터로 진행하는 1단계는 이 결정들과 병행할 수 있다. AWS 검증 환경과 리소스 범위는 5단계 전에 정한다.

## 구현 순서와 완료 기준

### 0. 사전 결정

최초 접수 작업과 병행해 운영자 초대 방식, 인증 주체와 영속 사용자 ID의 연결, 계정 복구·폐기 절차를 정한다. 기존 조직 인증을 연동할지 앱에서 개인별 계정을 운영할지는 2단계 구현 전에 확정한다. 4단계에는 개인정보와 삭제 기준이, 배포 검증에는 검증 환경과 목표 및 담당자가 필요하다. 이 항목의 승인 상태는 출시 기준 G0에 기록한다.

### 1. 최초 문의의 중복 접수 방지

[현재 접수 Service](../src/main/java/lab/helpdesk/ticket/application/TicketReceiptApplicationService.java)는 인증에서 확인한 고객 ID로 Ticket, 최초 Message와 AI Job을 한 트랜잭션에 저장한다. [접수 화면](../src/main/resources/static/ticket-ui.mjs)은 POST의 응답이 끊기면 결과 미확인을 표시하지만, 원래 제출을 다시 식별할 UUID는 없다.

아래는 PostgreSQL 접수에 적용할 권장 계약이다. 브라우저가 첫 제출에 `clientRequestId`를 한 번 만들고, 인증 고객의 영속 ID와 UUID 조합으로 그 제출을 찾는다. 제목과 본문은 파싱한 문자열을 저장 당시 원문과 그대로 비교한다. 공백이나 줄바꿈을 바꾸면 다른 내용이다.

| 접수 요청 | 응답 | 저장 결과 |
|---|---|---|
| 유효한 UUID로 처음 제출 | Commit 뒤 `201`과 문의 번호 | 접수 키와 Ticket 한 개, 최초 Message 한 개, AI Job 한 개 |
| 같은 고객이 같은 UUID·제목·본문으로 재확인 | `200`과 기존 문의 번호 | 추가 0건 |
| 같은 고객이 같은 UUID에 다른 제목이나 본문을 제출 | `409` | 기존 문의와 원문을 보존하며 추가 0건 |
| 같은 내용으로 새 문의를 명시적으로 제출하고 새 UUID 사용 | Commit 뒤 `201`과 새 문의 번호 | 별개 접수 한 건 |
| 전환 후 UUID가 없거나 형식이 잘못됨 | `400` | 추가 0건 |

`201`과 `200`에서 문의 번호와 기존 `Location` 규칙을 유지한다. 고객 화면의 문의 확인은 기존 '내 문의'와 연결한다. 다른 계정은 UUID를 알아도 원래 고객의 접수 결과를 읽을 수 없다.

#### 첫 구현 단위

1. **저장과 동시성.** V13의 기존 행을 유지하는 다음 Migration으로 접수 키를 추가한다. Ticket 행에 키를 함께 두는 안을 우선 검토한다. 고객 ID와 UUID의 조합을 PostgreSQL에서 유일하게 유지하고, 같은 키로 겹친 요청은 하나만 새 Ticket을 만든 뒤 나머지는 그 결과를 읽는다. 최초 Message와 AI Job도 같은 트랜잭션에서 저장한다. 독립 연결의 겹친 제출, 한 요청의 Rollback 뒤 다른 요청의 성공, Commit 실패 뒤 새 접수 키와 업무 행 0건을 테스트한다. 빈 DB 설치와 기존 V13 DB 업그레이드도 대조한다.
2. **API와 화면의 동시 전환.** [접수 Controller](../src/main/java/lab/helpdesk/ticket/web/TicketReceiptController.java)에 새 계약을 연결하고 PostgreSQL 화면, 테스트와 실습 스크립트의 호출을 함께 맞춘다. 설치된 구형 호출자가 있다면 전환 시점을 확인한다. 별도 `in-memory` 프로필의 제목 전용 실습은 기존 계약으로 검증한다. POST를 보낸 뒤 연결 끊김, 서버 오류 또는 응답 해석 실패로 결과가 불명확하면 같은 페이지 메모리에 원래 UUID·제목·본문을 유지한다. 사용자가 '접수 결과 확인'을 누르면 기존 로그인 세션에서 같은 제출을 보낸다. POST 전 CSRF 조회 실패는 미전송으로 안내한다. 재로그인이 필요하거나 페이지가 다시 열리면 '내 문의'와 운영자 확인을 안내한다. 새 세션으로 바뀐 경우 이전 세션의 제출이 다시 전송되지 않는지 확인한다.
3. **실제 브라우저와 DB 검증.** 첫 POST가 DB에 Commit된 뒤 브라우저가 응답을 잃는 상황을 합성 데이터로 재현한다. 화면에서 재확인해 `200`과 같은 문의 번호가 표시되고 DB의 Ticket·최초 Message·AI Job이 각 한 건인지 대조한다. 새로고침·재로그인 뒤에는 사용자가 내 문의에서 확인하며 자동 등록은 0건이다. CSRF 거부, 다른 고객의 조회 거부, 기존 문의 보존과 전체 Maven·Node·Lint 회귀를 함께 확인한다. 접수 완료 로그는 새 저장이 Commit된 경우에 한 번 남는지 확인한다. 결과는 [로컬 검증 안내](./local-verification.md)의 방식으로 남긴다.

접수 키는 문의에 연결해 유지하는 안으로 검토한다. 실제 운영의 보관·삭제 기간과 삭제 뒤에 도착한 재전송의 처리 기준은 G0에서 확정한다. [접수 결정과 대안](./pilot-decision-log.md#d01-최초-접수의-저장과-재확인)

### 2. 개인별 계정과 서비스 권한 운영

[현재 배포 인증](../src/main/java/lab/helpdesk/security/DeploymentSecurityConfiguration.java)의 설정 계정과 DB 영속 ID 연결을 바탕으로 개인별 계정을 운영한다. 운영자가 초대, 복구, 비활성화를 처리한다. 계정 관리 권한과 서비스 문의를 처리하는 지원관리자 권한을 각각 지정한다.

- 새 설치에서 최초 운영자와 지원 서비스를 구성하고, 인가된 운영자가 개인 계정을 초대하고 복구할 수 있다. 초대·복구·회수의 주체, 대상, 시각과 결과를 확인할 수 있다.
- 고객 A/B가 서로의 문의 URL을 직접 열거나 API를 요청해도 상대의 데이터가 노출되지 않는다. 검증 환경의 타 서비스 직원도 대상 서비스의 데이터를 조회하거나 변경할 수 없다.
- 서비스 권한 회수가 Commit된 뒤 시작한 요청에서는 기존 세션의 직원 조회·쓰기·재확인이 거부되며, 로그인 자격이 유효한 사람의 본인 고객 문의 권한은 기존 계약을 따른다. 계정 전체 비활성화는 새 로그인과 기존 세션의 보호 기능 접근을 막는다. 재시작 뒤에도 회수 상태를 유지하는지 확인한다. [서비스 권한 계약](./ticket-assignment.md)

### 3. 운영자의 일상 처리와 문의 누락 방지

기존 고객 화면과 직원 업무 목록을 시작 화면과 안내에 연결한다. 지원관리자가 오래된 미배정 문의와 권한이 회수된 직원의 남은 문의를 찾아 처리할 수 있게 한다.

- 고객이 접수한 문의를 내 문의에서 찾는다. 담당 직원이 배정과 인계, 공식 답변과 후속 글 확인을 수행한 뒤 관련 답변과 확인 범위를 근거로 해결한다. 고객의 명시적 재개까지 검증한다.
- 인계 뒤 현재 담당자만 새 공식 답변을 저장할 수 있고, 권한 회수 후 남은 문의는 같은 서비스의 지원관리자가 인계할 수 있다. 인가된 사용자는 기존 공개 범위 안에서 원문과 이력을 조회할 수 있다.
- 접수 실패나 결과 미확인의 화면에서 다시 조회할 곳과 운영자 문의 경로가 보인다. 지원관리자는 정해진 주기에 대기 문의를 확인하고, 운영 문제를 담당자에게 전달할 수 있다.

### 4. 개인정보와 운영 보호

수집 항목과 조회 권한, 문의 본문·업무 이력·AI 작업·로그·백업의 보관 범위와 기간을 정한다. 데이터 종류별로 삭제 또는 비식별화와 최소 감사 기록의 범위를 정한다. V12·V13의 확인과 해결 이력이 Message를 참조하므로 처리 후에도 승인된 범위의 이력이 유효하고 참조가 깨지지 않아야 한다. [상태 이력 스키마](../src/main/resources/db/migration/V13__add_ticket_status_events.sql)

- 합성 민감정보를 포함한 실패 사례에서 접근 거부 응답, 오류 응답과 운영 로그에 문의 원문이나 인증 값이 노출되지 않는다. 운영자는 요청 식별자로 원인을 추적한다.
- 승인된 담당자만 보관과 삭제 처리를 수행할 수 있고 승인·처리·검증 결과가 남는다. **삭제 전 백업**을 격리 DB에 복원한 뒤, 복원 시점보다 최신인 승인된 삭제 기록을 적용하거나 동등한 절차를 수행한다. 다시 열기 전에 고객·직원 화면과 API에서 삭제 내용이 재노출되지 않고 남겨야 할 이력 및 참조가 유효한지 검증한다.
- 승인한 기준을 넘는 반복 접수와 로그인 시도를 제한한다. 정상 고객의 접수 성공과 기존 문의 보존을 확인하고, 제한 발동의 근거를 운영 담당자가 확인할 수 있다.

### 5. 배포 후보 검증과 복구 훈련

[로컬 검증 안내](./local-verification.md)의 Maven, Node, Lint와 해당 Browser 검증을 후보 Commit 기준으로 확인한다. Commit, CI 실행, Image Digest, 실제 실행 중인 Digest와 설정 개정 식별자를 기록한다. [기존 재배포 안내](../deploy/ecs/README.md)를 참고해 승인된 검증 환경에서 HTTPS, 새 DB 설치와 Migration, 앱 상태와 로그를 점검한다.

- 빈 DB에 전체 Migration을 적용해 운영자와 지원 서비스를 설정하고, 합성 계정으로 접수부터 재개까지 검증한다. 학습용 스냅샷 이관을 검토할 때는 격리 복원본에서 소유권과 서비스 매핑을 대조한다. 확인된 근거로만 매핑하고, 미확인 행은 고객에게 공개되지 않는지 확인한다.
- **파일럿 후보에서 만든 백업**을 별도 DB에 복원한다. 4단계의 재노출 검증을 마친 뒤 Ticket, 최초 글, 답변, 소유권, 배정·상태·확인 이력을 대조한다. 복구 후 기존 문의 조회와 새 접수까지 측정하고, 앱 복귀 시 스키마 호환성을 확인한다.
- 후보의 Worker와 Provider가 모두 비활성이고 외부 AI 자격 증명이 주입되지 않았음을 설정과 실행 근거로 확인한다. 접수와 재시작을 포함한 검증 구간에서 외부 AI 연결 관찰 결과와 Job 상태·처리 시도 건수를 대조한다. 외부 호출과 Job 처리 시작은 각각 0건이어야 한다. 대기 Job은 건수만 관찰하고 활성화나 일괄 처리는 이후 승인 범위에서 결정한다.
- 운영자가 앱과 DB 상태 이상, 접수 실패와 장기 미배정 알림을 확인하고 담당자에게 전달하는 절차를 훈련한다. 재시작 뒤 재로그인과 문의 조회를 함께 점검한다.

## 파일럿 출시 기준

### 합성 검증의 잠정값

아래 값은 작은 규모로 검증을 시작하기 위한 목표다. 운영 책임자와 데이터 책임자가 실제 참여 인원, 예상 동시 사용량, 운영 시간·기간, 복구 목표와 예산을 승인표에 확정한다. 예상 부하나 복구 조건이 달라지면 확정한 조건으로 검증한다.

| 항목 | 검증 시작안과 측정 방법 |
|---|---|
| 참여 규모 | 고객 최대 10명, 담당 직원 최대 2명, 지원관리자 1명을 계획 상한의 초안으로 둔다. 합성 검증은 각 역할이 포함된 동시 5세션으로 시작한다. |
| 정상 요청 부하 | 동시 5세션으로 15분 동안 HTTPS 업무 API의 정상 읽기 300건 이상, 쓰기 60건 이상을 실행한다. 의도적으로 유도한 거부와 장애 사례는 따로 집계한다. |
| 응답과 오류 | 요청 전송부터 응답 수신까지 읽기 p95 500ms 이하, 쓰기 p95 1초 이하를 시작 목표로 둔다. 정상 구간의 예상 밖 응답 실패, 접수 누락·중복, 권한 위반은 0건이다. |
| 복구 | 데이터 손실 허용 범위(RPO)는 15분 이내, 복구 시간(RTO)은 90분 이내를 시작 목표로 둔다. 장애 전에 시간 간격을 두고 합성 문의를 접수한다. 모의 장애 시각과 복원본에서 확인한 마지막 합성 접수의 DB Commit 시각 차이를 기록한다. 복구 시간은 장애 선언부터 HTTPS 재로그인, 기존 문의 조회와 새 접수 성공까지 잰다. |

### 출시 승인표

후보별 기록에는 **Commit, CI 실행, Image Digest, 실행 환경과 설정 식별자, DB 스키마 버전, 실행 시각, 테스트 결과 위치와 관찰 값, 판정자**를 남긴다. 증거는 합성 ID와 비밀이 아닌 설정으로 남긴다. 아래 상태는 첫 후보를 검증하기 전의 상태다.

| 기준 | 통과에 필요한 증거 | 확인 담당 | 현재 상태 |
|---|---|---|---|
| G0 범위와 정책 | 대상 서비스, 계정·세션 방식, 참여자 상한과 운영 시간, 데이터 보관·삭제 절차, 승인 담당자, 부하·복구 목표 및 예산 확정 기록 | 서비스 운영 책임자와 데이터 책임자 | 결정 대기 |
| G1 접수와 재확인 | 동일 접수의 `201/200`, 내용 변경 `409`, DB의 중복 제약과 저장 경계, 동시 요청 및 응답 유실 뒤 동일 ID와 DB 건수, Rollback 뒤 새 제출 기록과 업무 행 0건, 재로그인 뒤 조회 경로 | 개발 담당자 | 검증 대기 |
| G2 권한과 업무 | 역할별 API·Browser 결과, 계정 비활성화와 서비스 권한 회수 뒤 기존 세션의 보호 기능 차단 범위, 접수부터 재개까지의 이력 | 개발 담당자와 서비스 운영 책임자 | 검증 대기 |
| G3 데이터 보호 | 접근 거부 및 운영 로그의 비노출 대조, 합성 데이터 삭제 후 격리 복원, 재노출 및 참조 무결성 검사 | 데이터 책임자와 운영 담당자 | 검증 대기 |
| G4 배포와 복구 | 검증한 Digest와 실행 Digest 일치, 신규 DB 기동, HTTPS와 Migration, 합의 부하에서의 관찰 값, 복원 및 앱 복귀 증거와 RPO/RTO 충족 | 운영 담당자와 개발 담당자 | 검증 대기 |
| G5 AI와 중지 대응 | Worker·Provider 비활성, AI 자격 증명 미주입, 외부 연결 관찰 및 Job 시도 대조에서 호출·처리 시작 0건, 대기 Job 수, 담당자 알림과 신규 접수 중지·재개 훈련 | 운영 담당자 | 검증 대기 |

G0~G5의 증거를 확인한 뒤 서비스 운영 책임자와 데이터 책임자가 승인 시각과 범위를 기록한다. 그 승인 범위에서 실제 문의를 받기 시작한다. 이미지, 스키마 또는 설정이 바뀌면 영향을 받는 검사를 새 후보에서 다시 실행한다.

파일럿 중 권한 우회, 개인정보 재노출, 승인 범위 밖 AI 호출, 접수 중복·누락을 확인하면 운영 담당자가 정해진 절차로 신규 접수를 중지한다. 가용성 중지 기준의 시작안은 상태 점검이 5분간 연속 실패하는 경우다. 권한 우회나 데이터 노출이 있으면 문제가 된 조회 등 접근 경로도 차단한다. 운영 담당자는 기존 문의와 필요한 증거를 보존하고 책임자에게 보고한다. 수정 후보에서 해당 기준을 다시 통과하고 운영 승인을 받은 뒤 접수를 재개한다.

파일럿 종료 때 접수 누락·중복, 권한 사고, 미배정 문의, 첫 답변 시간과 해결·재개 사례를 운영 기록과 대조한다. 승인한 조건과 관찰 결과에 따라 계속 운영할지, 수정 후 다시 검증할지 결정한다.

## 첫 파일럿 이후 검토

- 고객 답변 및 담당자 인계 알림, 여러 자사 앱에서 같은 Helpdesk로 접수하는 연동은 파일럿에서 확인한 업무 필요에 따라 순서를 정한다.
- 실제 문의에 AI를 적용할 때는 외부 전송 범위, 개인정보 검사 실패 시 차단, 출력 품질과 호출 한도를 별도로 검증한다. 파일럿 기간에 쌓인 문의를 AI 처리 대상으로 삼을지 명시적으로 결정한다.
- 첨부와 비공개 내부 메모, 여러 독립 조직에 제공하는 SaaS는 각 데이터와 권한 경계가 정해진 뒤 별도 계획으로 다룬다.
